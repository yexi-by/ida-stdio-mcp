## 固定环境

- Python 3.13。
- `uv` 管理锁文件、工作树外开发环境、构建和隔离安装。
- `mcp==1.28.0`。
- Ruff、basedpyright strict、pytest 与 Hypothesis。
- LLVM/LLD 22.1.8 构建项目自有 fixture。
- IDA Pro 9.3+ headless；涉及反编译的门禁还要求有效 Hex-Rays 许可。
- Windows 本机 x64 debugger 门禁必须在自托管 Windows runner 上执行。

开发环境必须位于工作树外。例如：

```powershell
$env:UV_PROJECT_ENVIRONMENT = Join-Path $env:LOCALAPPDATA "ida-re-mcp/dev-venv"
```

workspace、日志、artifact、checkout、staging 和测试运行数据同样不得写入工作树。

## 普通质量门禁

在仓库根目录执行：

```powershell
./scripts/run_quality.ps1
```

该脚本必须依次完成：

1. 安装并确认 Python 3.13；
2. 校验锁文件并按锁文件同步依赖；
3. Ruff 格式检查与静态检查；
4. basedpyright strict；
5. unit 与 integration 测试；
6. fixture 双目录可复现构建校验；
7. wheel 构建；
8. 在一次性工作树外环境安装 wheel；
9. 以安装后的 `ida-re-mcp` 执行真实 stdio smoke。

任一步失败都使普通质量门禁失败。临时测试目录必须在结束时清理，仓库内不得留下缓存、
虚拟环境或运行产物。

## MCP 标准门禁

MCP 测试以 2025-11-25 稳定规范和官方 Python SDK 1.28.0 为基准，必须验证：

- 服务使用官方 `Server`、stdio transport 和标准初始化生命周期；
- 客户端完成初始化与能力协商后，只能观察到服务实际注册的 tools 与 resources；
- `tools/list` 目录在进程启动后固定、确定性排序，并与工具注册状态一致；
- 所有工具输入和结构化输出都经过服务端 JSON Schema 2020-12 校验，根对象封闭；
- 成功结果同时提供规范化 content 与 structured content；工具参数的 input schema
  校验失败和业务执行失败使用 `isError=true`，错误对象只放入 text content，
  不与成功态 output schema 冲突；
- CallToolRequest 结构错误、未知工具和无效 resource URI 使用 `-32602`，resource
  不存在使用 `-32002`，未捕获内部异常使用脱敏后的 `-32603`，各类错误保持边界；
- `resources/list` 与 `resources/read` 能读取不可变 artifact，文本与二进制内容使用规范字段；
- 大结果转为 artifact，单个 resource chunk 不超过 1 MiB；
- 真实子进程覆盖并发、取消、EOF、异常退出和 stdout 协议纯净；
- Codex、OpenCode 与 MCP Inspector 的主机验收在工作树外执行并保存独立证据。

主机验收不能用直接调用 Python 对象替代；必须启动构建产物中的 CLI 并通过真实 stdio
交换消息。stderr 和平台日志可以包含诊断，stdout 只能包含协议帧。

## Workspace、operation 与 revision 门禁

必须验证以下不变量：

- data root 只有一个有效 Supervisor owner，失效 lease 的接管可审计；
- 原始样本在 `workspace.create` 时复制并校验 SHA-256，之后保持只读；
- operation 只沿规定状态机前进，重启恢复不会伪造成功或已取消状态；
- 同一 workspace 严格串行，不同 workspace 只在 worker 配额内并行；
- AnalysisWorker 与 DebugWorker 使用私有 checkout，关闭时不发布热状态；
- MutationWorker 依次执行 CAS、staging、预检、批量写入、回读、保存、冷验证、原子发布
  和 HEAD CAS；
- 在预检、写入、保存、冷验证、发布和 HEAD CAS 各阶段注入异常或强杀后，旧 revision、
  HEAD 和原样本摘要均不改变；
- 并发写者在相同 base revision 上至多一个成功；
- GC 永不删除 current revision 或 pinned export，并能安全回收失去引用的 staging、
  checkout、operation 和 artifact。

## Fixture 门禁

fixture 必须由仓库中的自有源码和生成脚本构建，不下载或执行互联网样本。PE x64、ELF
x64、AArch64 ELF、IL2CPP-shaped C++ 和 Windows x64 debugger fixture 的二进制及
SHA-256 必须与工具链清单一致。

执行：

```powershell
./scripts/build_fixtures.ps1
./scripts/check_fixture_reproducibility.ps1
```

两个独立目录的构建结果必须逐字节一致。IDA 测试只打开复制到临时目录的私有 fixture，
测试前后仓库中的 fixture 文件集合和摘要必须相同。

## IDA 静态分析与写回门禁

在装有受许可 IDA Pro 9.3+ 和 Hex-Rays 的自托管 runner 上设置 `IDADIR`，执行：

```powershell
uv run --locked pytest -q tests/ida -m "ida and not debugger"
```

证据必须来自真实 headless worker，并覆盖：

- 程序概览、段、入口、导入导出、重定位、异常与 unwind、函数和字符串；
- 非连续函数 chunks、指令操作数、code/data xref、CFG 与 call graph；
- UDT、函数原型、栈变量、lvar 和 ctree 多对多地址映射；
- 函数内 MAY/MUST def-use、有界 slice 和 unknown barrier；
- `change.prepare` 的 canonical operations、digest、preimage 与 base revision 绑定；
- refine、类型写回、IL2CPP 原生注解和 inverse change 的 staging 发布；
- 保存后重新打开的冷验证、组件哈希和 revision 原子发布。

不得用整段伪代码文本快照作为通过依据，也不得以 mock IDA API 代替此门禁。

## Windows x64 动态调试门禁

在 Windows 本机 x64、自托管且具有有效 IDA debugger 环境的 runner 上执行：

```powershell
uv run --locked pytest -q tests/ida -m "ida and debugger"
```

必须观察到真实 IDA debugger 事件，并覆盖：

- backend headless 加载以及 PROCESS_STARTED 或 PROCESS_ATTACHED；
- module/image + RVA 在 ASLR 下解析为运行时地址；
- 断点进入 active 后产生真实 BREAKPOINT；
- suspended stop 上的 RIP、RSP、线程、调用栈、栈内存和已知内存读取；
- pause、continue、step-into、step-over 与 run-to；
- 正常退出、detach、非法 PID、目标提前退出和无效内存；
- worker 崩溃后 Job Object 清理本服务启动的目标进程；
- 全程无 GUI、弹窗或 stdout 污染。

`debug.establish`、`debug.control` 和 `debug.finish` 只有在事件泵观察到对应状态转换后才算
完成。读取寄存器、线程、栈和内存必须绑定有效 suspended `stop_id`。

## 发布门禁

发布候选必须按以下顺序取得并保存证据：

1. 普通质量门禁；
2. MCP 真实 stdio 与主机验收；
3. fixture 可复现性；
4. IDA 静态分析与事务写回；
5. Windows x64 动态调试；
6. wheel 隔离安装后的最终 smoke；
7. 文档、能力矩阵和实际工具目录的一致性复核。

上述门禁均已在 2026-07-25 的本机环境通过。`1.0.0` 正式发布仍需在拟发布提交上重新
执行相同门禁，并完成版本号、构建产物与发布元数据复核。
