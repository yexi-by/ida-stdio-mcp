# 架构

## 进程边界

```text
MCP stdio
  → Supervisor
      → WorkspaceRegistry
      → OperationCoordinator
      → ArtifactStore
      → AnalysisWorker / MutationWorker / DebugWorker
```

Supervisor 负责 MCP、策略、workspace、operation、artifact 与 worker 编排，不导入
`idapro` 或 `ida_*` 模块。worker 使用 IDA 实际绑定的 Python 3.13 运行时，所有 IDA
API 调用都发生在 owner 线程。

Supervisor 与 worker 使用当前用户私有的本地 IPC：Windows 使用 AF_PIPE，消息是带
随机鉴权值的 UTF-8 JSON bytes。IPC、worker stdout/stderr 和 MCP stdout 相互分离。

每条 MCP stdio 连接拥有独立 session root 与 Supervisor owner lease。operation、
change set、cursor 私钥、checkout、temp、IPC、worker 日志和调试状态全部落入该
session；不同连接不会读取或修改彼此的会话态。workspace、不可变 revision 与 artifact
位于共享 data root，同一 workspace 的完整 worker 生命周期由跨进程 lease 严格串行，
revision 发布继续使用 CAS。多个 Codex/OpenCode Agent 因而可以同时连接同一部署，
而不会共用 checkout、operation 或调试状态。

session owner lease 位于 `data_root/session-leases`，不放在待回收的数据树中。`gc`
取得该 lease 后，以 session 数据与日志树中的最后活动时间判定保留期，并在释放 lease
前完成删除；活动连接不会被误删。活动 workspace 创建和活动 worker lifecycle 也由
独立 lease 保护。超过 operation 保留期且仍未发布首个 revision 的崩溃 workspace 会在
取得 workspace lease 后回收。

artifact 与 ChangeSet GC 在取得 workspace lifecycle lease 后重新读取已发布 revision，
不使用锁外旧快照决定删除范围。Analysis/Mutation/Refine/Expert/Bootstrap/Doctor 与
Debug worker 还必须取得共享 data root 下对应的全局 slot lease；配置的 worker limit
因此在正常启动、取消、超时和有序关闭期间是整个部署的并发上限，而不是单个
Supervisor 的局部上限。Supervisor 被强杀时文件 lease 会由操作系统回收，但已进入
handler 的孤儿 worker 可能短暂继续运行；该窗口不宣称实际 IDA 进程数的硬保证。

每个活动 worker 只打开一个 workspace 的私有 IDB checkout。同一 workspace 由生命周期
锁严格串行；不同 workspace 可按部署级许可证与 worker 上限进程级并行。
AnalysisWorker 按 `workspace_id + revision` 持久复用私有 checkout，默认空闲 300 秒后
退出；worker 失败或请求取消会立即丢弃该 session 与 checkout。

## MCP 边界

服务使用官方稳定 Python MCP SDK 的低层 Server 与 stdio transport。标准
`initialize`/`notifications/initialized` 生命周期、协议版本协商、请求取消和 JSON-RPC
读写均由 SDK 负责；项目不复制这些机制。`tools/list` 返回启动时固定、按名称排序的
工具目录。

初始化只广告 tools 与不可变 resources，不广告 Tasks、prompts、sampling、
completions、subscriptions 或交互式审批。长操作使用产品内 operation 状态机：

```text
queued → running → cancel_requested → succeeded | failed | cancelled
```

取消请求只表示 `cancel_requested`。执行器完成清理并确认后才能进入 `cancelled`。
`operation.wait` 的 `wait_ms=0` 是查询，长轮询最多 30 秒。
长轮询使用可取消的短周期状态读取；MCP 请求取消后不会留下占用线程池的阻塞 wait。
operation 记录原子写入当前连接的 session 目录并保留 24 小时。新的 stdio 连接使用
新的 session，不能查询或取消旧连接的 operation；旧 session 的记录只用于保留期与
垃圾回收。已经原子发布的 revision 不依赖旧 operation 会话，仍可从共享 workspace
读取。

所有工具输入输出使用独立、封闭的 JSON Schema 2020-12。静态查询显式绑定
`workspace_id` 与 `revision`；cursor 还绑定查询摘要，revision 或查询改变后立即失效。
`workspace.get` 的 revision 摘要同样使用 cursor 与 page size，并在达到 inline 预算前
自动缩短当前页。
超过 inline 上限的结果保存为不可变 artifact，并通过 `ida-re://...` resource URI
读取。UTF-8 文本 artifact 返回 MCP text content，其他内容返回 blob。公开 payload
超过 1 MiB 时返回
`application/vnd.ida-re.chunked-artifact+json` 索引；索引列出每个 chunk 的 URI、
offset、size 与 SHA-256，单个 resource chunk 不超过 1 MiB。公开 chunk index 与内部
artifact manifest 使用相互独立的 schema version。

成功工具结果的 structured content 必须符合该工具的 output schema。工具参数的
input schema 校验失败与业务执行失败使用 `isError=true`，稳定错误对象只放在 text
content 中，使 Agent 能据此修正调用；CallToolRequest 结构错误、未知工具和无效 resource
URI 使用 JSON-RPC `-32602`。内部异常使用脱敏后的 `-32603`，resource 不存在使用
`-32002`，完整性或解码失败属于内部错误。

## Workspace 与 revision

`workspace.create` 将样本复制为平台数据目录中的私有候选副本并验证 SHA-256，不修改
调用方路径。服务只在候选副本上执行严格的 PE/ELF Native 格式预检；调用方提供的必须
是可由 IDA 直接加载的 Native 镜像。shell 脚本、gzexe 和其他压缩包装器稳定返回
`unsupported`，服务不解包、不执行候选文件，也不会为不受支持的输入发布 workspace。
已发布 revision 是不可变冷存档。AnalysisWorker 和 DebugWorker 从冷 revision 创建
私有 checkout，关闭时始终不保存，避免自动分析、反编译缓存或 debugger rebase 改变
已发布数据库。

MutationWorker 的发布顺序固定为：

1. CAS 校验 `expected_revision`；
2. 从冷 revision 创建同卷 staging；
3. 完整预检全部操作；
4. 批量应用并回读验证；
5. 保存并关闭数据库；
6. 重新打开做冷验证和组件哈希；
7. 原子发布候选 revision；
8. CAS 更新 workspace HEAD。

任一步骤失败只丢弃 staging，样本摘要、已发布 revision 和 HEAD 保持不变。同一
workspace 的并发写者只有一个能通过 CAS。每个候选 revision 在发布前由新的 transient
AnalysisWorker 冷打开，重新核对原样本 SHA-256、架构、位宽、端序、镜像大小和 IDB
组件哈希；不能依赖 mutation worker 的热状态完成验证。

## 静态分析

静态 worker 返回 IDA 原始事实，Supervisor 负责将其转换为严格公开模型：

- 地址采用 image+rva、database+ea、file+offset 的判别联合；
- 函数范围保留非连续 chunks；
- CFG、调用和 xref 图有节点与深度硬上限；
- 未解析间接调用显式降低 coverage；
- ctree 地址映射允许多对多；
- dataflow 只描述函数内 microcode 的 MAY/MUST def-use 与有界 slice；MUST 在 CFG 上
  对 reaching definition 做全路径固定点证明，forward 与 backward 共用同一唯一性语义；
- 汇合路径定义不一致时不产生 MUST 边；未知调用、内存别名和分析上限形成明确 barrier，
  达到 `max_steps` 返回部分结果而不是能力错误。

`coverage` 与 `provenance` 是结论可信边界，不是装饰字段。

## 动态调试

DebugWorker 独占私有 checkout 和一次调试会话，并持续驱动 IDA 真实事件泵。状态为：

```text
launching → running ↔ suspended → exited | detached | lost | failed
```

`debug.establish`、控制动作和 `debug.finish` 只有观察到对应事件或规范允许的运行状态
观察后才完成。它们返回 `completion_kind`、`completion_provenance` 与
`observed_event_sequence`，让调用方把完成结果与事件流中的证据精确对应。每次
suspended 生成新的 `stop_id`；恢复运行后，此前的 stop 不再有效。寄存器、线程、
调用栈、内存映射和最多 64 KiB 的内存读取只允许在匹配的 suspended stop 上执行。

事件的 `provenance` 明确区分 `ida_event`、`state_observation` 与 `service_event`。
真实 IDA 事件必须携带 `event_id`；IDA 不提供 resume event 时，只能把观察到的
`DSTATE_RUN` 记录为 `state_observation/execution_resumed`，不能伪装成 IDA 事件。

断点使用 image/module + RVA，模块加载后解析 ASLR 运行时地址。首版控制动作只有
`pause`、`continue`、`step_into`、`step_over` 与 `run_to`。

动态调试只承诺 Windows 本机 x64。服务启动的目标进入 Job Object，以便 worker 异常
退出时回收进程树；Job Object 不提供恶意样本沙箱。

## 运行数据

配置、workspace、revision、artifact、checkout、日志、临时文件和开发虚拟环境都位于
工作树外的平台用户目录。仓库只保存源码、自有 fixture 源码、可复现 fixture 二进制、
测试、文档和构建定义。
显式 data/log root 不得是文件系统根目录，也不得与工作树形成任一方向的包含关系。

GC 只能由 data root owner 运行，并在 workspace 生命周期锁下计算保留集合。current、
最近配置数量的 revision 与 pinned export 受保护；只回收未保留 revision、孤立
artifact、change set/staging，并在 apply 模式清理过期 operation。软配额只报告压力，
不会越过保护集合自动删除数据。
