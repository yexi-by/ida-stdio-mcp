## 官方约束提炼

### Headless 与 GUI

本项目底线是完全不依赖 IDA GUI。官方资料对项目的直接含义是：

- `-A`/autonomous mode、`-S` 脚本执行、`-T` loader 指定、`-O` 插件选项和日志参数必须能通过配置或 API 链路进入 IDA。
- 任何需要弹窗选择 loader、processor、debugger、attach 进程、异常处理策略的流程，都不是合格的 headless 流程。
- 若 IDA 当前环境没有调试后端，必须返回 `unsupported` 和诊断字段，不能静默假装启动成功。
- 文档、README、skill 和错误提示都必须明确：GUI 只可作为人工外部排障工具，不是项目运行依赖。

### 动态调试

动态调试不只是调用 `ida_dbg.start_process`。项目必须先证明：

- 调试器 backend 已加载且可用。
- `start_process`/`attach_process` 请求已被 IDA 调试器接受。
- 当前进程状态、线程数、事件、寄存器/栈/内存读取在同一会话内真实可用。
- 本地调试与远程调试的参数模型不同，远程场景不能用本地启动参数硬套。

因此，“backend unavailable”不是 GUI 问题本身，而是 headless 调试链路缺少可加载/可诊断后端的问题。正确处理方式是程序化加载、显式诊断、按官方参数暴露配置，并为 Windows/Linux/local/remote 分别验收。

### MCP stdio

MCP `2025-11-25` 对 stdio 的关键约束：

- JSON-RPC 消息使用 UTF-8。
- stdio 消息按换行分隔，消息内不得包含嵌入换行。
- 服务端 stdout 只能输出有效 MCP 消息。
- 日志可以写 stderr；客户端不应仅因 stderr 有输出就视为错误。

这意味着项目如果继续保留 `Content-Length` framed 传输，只能标记为兼容旧客户端或项目私有兼容层；若宣称跟随最新 MCP stdio，就应把 newline JSON-RPC 作为默认或至少作为明确模式。

### 工具输出与错误

MCP 工具调用的业务失败应回到 tool result，而不是一律抛协议级 JSON-RPC 错误。项目里的 `status`、`warnings`、`error`、`data` envelope 与 MCP `structuredContent` 可以形成稳定映射：

- 找不到工具、协议不支持、消息格式非法：协议级错误。
- IDA 无调试后端、Hex-Rays 不可用、目标文件打不开、分析失败：工具结果内显式失败。
- 可降级但仍有部分结果：工具结果内带 `warnings` 和受限 `data`。

## 对项目缺口的分级

### 硬缺口

- Headless 动态调试 backend 的加载、状态检测和诊断链路必须完整。
- `debug_launch`/`debug_attach` 后续寄存器、栈、内存、断点工具必须基于同一个真实调试会话。
- AGENTS/README/skill 必须写明“不依赖 IDA GUI”是项目底线。
- 文档必须区分官方 latest `2025-11-25` 与项目当前兼容配置 `2025-06-18`；是否升级协议属于单独兼容决策，不是 IDA 能力初始化硬依赖。

### 条件缺口

- `open_target` 是否需要暴露 `-T` loader、`-p` processor、`-O` plugin options，取决于项目是否承诺处理多 loader、大 PDB、语言插件和特殊文件类型。
- 远程动态调试是否纳入验收，取决于项目是否承诺 remote debugger；若承诺，就必须按官方 `-r`/remote 模型补参数与测试。
- Hex-Rays batch decompile 是否做成独立批处理入口，取决于项目是否承诺“脱离交互式会话批量反编译”。

### 不是当前缺口

- C++ SDK 不是本 Python 项目的主线缺口。
- IDA GUI 教程、菜单操作和交互窗口说明不是本项目运行依赖。
- MCP experimental tasks、draft features 和非 stdio HTTP 能力，不应在没有产品承诺时算作缺口。
- IDA Domain microcode 当前可作为实验性线索；只要不宣称稳定修改/写回能力，就不是硬缺口。
